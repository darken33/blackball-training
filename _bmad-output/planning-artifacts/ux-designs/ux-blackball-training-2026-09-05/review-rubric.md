# Spine Pair Review — blackball-training

## Overall verdict
The DESIGN.md/EXPERIENCE.md pair is a disciplined, well-inherited spine: all three UJs are flowed with named protagonist/climax/failure paths, every color/typography/rounded/spacing/component token resolves, component names are identical across both files, and canonical section order is intact in both documents. The blocking issues are narrow but real: three interactive elements referenced in EXPERIENCE.md (the Accueil level-select buttons, the resume banner, the "Rejouer l'essai" button) have no row in either spine's Components section, and no contrast target is stated anywhere — a computed check on the stated hex values finds the primary CTA's text (`accent-primary-contrast` on `accent-primary`) at 4.49:1, marginally failing WCAG AA. Neither issue is architectural; both are fixable inside the spine pair before handoff.

## 1. Flow coverage — strong
Extracted UJ-1 (séance Bronze), UJ-2 (exercice Argent multi-billes), UJ-3 (consulter progression) from PRD §2.3. All three have a matching Key Flow in EXPERIENCE.md with named protagonist (Fifi), numbered steps, an explicit **Climax** beat, and a failure/edge path where the source specifies one (UJ-1's "cas limite" abandon → Flow 1's abandon note; UJ-3's first-use empty state → Flow 3's closing line).
### Findings
- **low** Flows aren't cross-labeled with their UJ id (e.g. "Flow 1 (UJ-1)") (EXPERIENCE.md lines 92, 104, 111). *Fix:* add the UJ id in the flow heading for faster traceability — optional, the example spines don't do this either.

## 2. Token completeness — adequate
Extracted all `colors`/`typography`/`rounded`/`spacing`/`components` frontmatter keys and every `{path.to.token}` reference in both files' prose and component blocks (DESIGN.md lines 62–132; EXPERIENCE.md frontmatter lines 5–6). Every reference resolves to a defined token; no missing hex values; typography correctly stays semantic (platform-native notes) per spec. No dark/light pairs needed since the product has no light mode (documented assumption). The gap is contrast: no numeric target is stated anywhere, even though EXPERIENCE.md's Accessibility Floor explicitly defers contrast to DESIGN.md.
### Findings
- **high** No contrast ratio/target is stated for any color pair, and a computed check on the stated hex values shows `accent-primary-contrast` (`#F4F1E8`) on `accent-primary` (`#2F7D46`) — the fill/text pair for the "Next exercise button," the single most emphasized action in the app (DESIGN.md lines 85–86, 148) — is 4.49:1, marginally under WCAG AA's 4.5:1 for normal text (DESIGN.md colors block lines 15–16; Accessibility Floor cross-reference at EXPERIENCE.md line 82). *Fix:* state an explicit contrast floor (e.g. "AA 4.5:1 for all text-on-fill pairs") in DESIGN.md.Colors and nudge `accent-primary-contrast` or darken `accent-primary` slightly to clear it with margin.
- **medium** `ball-black` (`#141414`) and `ball-red` (`#C1272D`) against `table-felt` (`#154A2E`) compute to ~1.8:1 and ~1.75:1 contrast — the table-diagram is the app's core informational surface and DESIGN.md's own stated goal is legibility "sous l'éclairage tamisé d'une salle de billard" (DESIGN.md line 111), yet no ball outline/stroke token exists to guarantee the black ball stays visible against dark felt regardless of ambient light (DESIGN.md components.table-diagram, lines 93–100; ball colors lines 27–30). *Fix:* either state that fidelity to official ball colors overrides the dim-light legibility goal for this one component (an explicit trade-off), or add a thin outline token (e.g. `ball-outline`) to the `table-diagram` component spec.

## 3. Component coverage — thin
Extracted every component name used anywhere in both files. DESIGN.md.Components and EXPERIENCE.md.Component Patterns agree perfectly on 8 named components (Score bar, Essai button, Fault button, Undo banner, Next exercise button, Exercise card, Table diagram, History row) — each with real behavioral and visual rules, not one-word descriptions. But three UI elements are named and used in EXPERIENCE.md's IA/State Patterns/Key Flows without ever getting a row in either spine's component tables.
### Findings
- **high** The Accueil level-select buttons ("3 boutons niveau (Bronze/Argent/Or), seuil rappelé sous chaque bouton") are the primary entry action of the entire app — reached on every cold app open — yet have no row in DESIGN.md.Components or EXPERIENCE.md.Component Patterns: no fill/border/radius, no tap behavior beyond "choisir un niveau" (EXPERIENCE.md IA line 23; State Patterns line 63; DESIGN.md Components lines 142–152 — absent). *Fix:* add a "Level button" row to both tables (visual spec: likely reuses `exercise-card` or a dedicated surface; behavioral spec: tap → starts session at that level's first exercise).
- **medium-high** "Rejouer l'essai" is named as a distinct proposed action in State Patterns ("si essais restants (< 3) et score non maximal, 'Rejouer l'essai' proposé à côté d'\"Exercice suivant\"", EXPERIENCE.md line 66) but has no visual spec and no behavioral rule beyond that one clause — it's unclear whether it shares the `next-exercise-button` style (implying two prominent full-width accent buttons side by side) or is a secondary/outline variant. *Fix:* add a row (or an explicit note under Next exercise button) specifying its visual treatment relative to the primary action.
- **medium** The Accueil resume banner ("Reprendre la séance [Niveau] — exercice X/N") appears in IA (EXPERIENCE.md line 24) and State Patterns (line 64) as a persistent, load-bearing UI element (it's how an interrupted session is found again) but has no row in either spine's component tables — unlike the visually similar `Undo banner`, which is fully specified. *Fix:* add a "Resume banner" row; likely reuses `surface-overlay` + `rounded/lg` in the spirit of `score-bar`, but this should be stated, not inferred.

## 8. Shape fit — adequate
DESIGN.md's eight sections appear in exact canonical order (Brand & Style → Colors → Typography → Layout & Spacing → Elevation & Depth → Shapes → Components → Do's and Don'ts). EXPERIENCE.md's required defaults are all present and correctly ordered (Foundation, IA, Voice and Tone, Component Patterns, State Patterns, Interaction Primitives, Accessibility Floor, Key Flows). Responsive & Platform is correctly omitted (single-surface mobile, no breakpoints). The one dropped-default worth a second look is Inspiration & Anti-patterns.
### Findings
- **low** Inspiration & Anti-patterns is omitted entirely, but the project clearly has reject-worthy content: an explicit anti-gamification stance runs through Brand & Style ("Aucune mascotte, aucun badge, aucun compteur de série," DESIGN.md line 109, directly tied to SM-C1) and Interaction Primitives' "Banni" list (carrousels, animations d'ouverture, badges, compteurs de série, notifications push — EXPERIENCE.md line 78). This is materially the same kind of content Quill's Inspiration section consolidates under "Rejected — Streaks (Duolingo, most habit apps)." Here it's scattered across three places instead of named once. Defensible (no competing product was actually studied and rejected — the F.F.B. règlement is the only real reference, and it's a rulebook, not a UX competitor), but a downstream reader scanning for "what patterns are deliberately excluded and why" won't find one section that answers it. *Fix:* either add a short Inspiration & Anti-patterns section consolidating the anti-gamification stance (citing SM-C1), or leave as-is and accept the scatter as intentional.

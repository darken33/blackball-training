# Review — ARCHITECTURE-SPINE.md (Carnet de Score Blackball DFA)

## Verdict

The spine is well-formed in style (terse, tabular, rationale correctly parked in the memlog) and its six ADs correctly cover the score/persistence/dependency invariants — but it ships with two concrete, evidence-backed defects (a catalog-ID convention that cannot represent 20 of the 35 exercises, and an ER field that contradicts its own AD-4 delete rule) and one skipped structural dimension (the deployment/hosting envelope, decided only in the memlog and referenced obliquely rather than stated). Not yet safe to hand to epics/stories without a fix pass.

## Findings

### 1. [CRITICAL] The exercise-ID convention is unable to represent Bronze content — it only identifies the Figure, not the Exercise

The Consistency Conventions table defines exercise IDs as `{niveau}-{lettre}` (minuscule), giving `bronze-a` as the worked example. This is correct for Argent and Or, where "one diagram = one exercise" (confirmed in content-catalog.md §0 and §5: Argent A-I and Or A-F are each a single exercise). It is wrong for Bronze: per the PRD Glossary (§3, "Figure") and FR-1's own text ("Bronze compte 20 exercices (Figures A-F)"), a Bronze Figure is shared by *several independent exercises* — content-catalog.md §5 confirms Figure A alone contains four distinct exercises (A1-A4, different balls/pockets/quantités-de-bille, hence different content and potentially different scores across a session), and the scoresheet layout note ("4 rows for A/B, 3 rows for C/D/E/F, 20 rows total") confirms every one of the six Bronze figures holds 3-4 exercises. Under the stated convention, `bronze-a` cannot disambiguate A1 from A2/A3/A4 — the catalog key and persistence foreign key (per the same table row) would collide for all 20 Bronze exercises. This is exactly the kind of consistency convention the spine exists to fix, and as written it is actively broken for more than half the catalog (20/35 exercises). Fix: extend the convention for Bronze to `{niveau}-{figure-lettre}{exercice-numero}` (e.g. `bronze-a1`) or an equivalent two-level key, and correct the worked example.

### 2. [HIGH] SESSION's persisted `abandonnee` boolean contradicts AD-4's own "suppression" rule

AD-4's Rule states plainly that "la suppression d'une session en cours n'existe que dans le handler de confirmation du bouton 'Abandonner'" and that no other code "ne mute ni ne supprime une session en cours" — i.e., abandon = delete the row. FR-8 backs this: an abandoned session leaves the historique untouched and "rien n'est conservé de sa progression partielle." Yet the ER diagram in the same document models `SESSION { ... boolean abandonnee }` as a persisted field. If abandon is implemented as AD-4 describes (delete), a persisted `abandonnee=true` row can never exist to read — the field is dead weight at best, and at worst signals that whoever modeled the schema actually intended a soft-delete (mark-and-retain) rather than the hard delete AD-4's prose promises. A downstream implementer hits a real fork here: call `session.delete()` (matching AD-4's words) or `session.update({abandonnee: true})` (matching the ER diagram)? These have materially different consequences (data genuinely gone vs. retained on-device, historique queries needing an extra filter vs. not). Fix: remove `abandonnee` from the ER diagram if AD-4's hard-delete rule is what's intended (the field is unreachable/dead under that rule), or, if soft-delete is actually wanted, rewrite AD-4's Rule to say so and update its Prevents clause and FR-8's "rien n'est conservé" framing accordingly.

### 3. [HIGH] Deployment/hosting is decided in the memlog but never stated as a decision in the spine body, and its interaction with the offline-PWA NFR is unaddressed

The memlog records an `[ASSUMPTION]` decision: static build deployed to GitHub Pages via GitHub Actions on push to main. This decision does not appear anywhere in the spine's visible sections (no Stack row, no dedicated section) — it only surfaces as a half-sentence inside **Deferred**: "au-delà du principe 'GitHub Actions build+deploy vers GitHub Pages', le détail du workflow YAML est un détail d'implémentation," phrased as if the principle had already been established earlier in the document, which it has not. This is precisely the "operational/environmental envelope" dimension the checklist asks to verify is not skipped: a reader of the spine alone (the artifact meant to govern the level below) has no place where hosting/deploy is actually decided. Beyond the presentation gap, the choice itself has an unaddressed architectural consequence: GitHub Pages project-page hosting serves the app from a URL subpath (`username.github.io/repo/`), which constrains the PWA manifest's `scope`/`start_url` and Vite's `base` config — get these wrong and the installable/offline behavior (the app's core NFR, backed by `vite-plugin-pwa` in the Stack) silently breaks. The spine names the hosting target but never states the convention needed to keep it compatible with the offline-PWA invariant it otherwise protects carefully (AD-2, AD-3). Fix: promote the deployment decision into the spine body (a short "Deployment" row/section, or fold into Stack), and add a one-line convention pinning base path/manifest scope to the GitHub Pages project-page layout.

### 4. [MEDIUM] AD-4's enforcement mechanism is weaker than its siblings (AD-1, AD-5) on the same axis — discipline, not structure

AD-1 and AD-5 both push their invariant into a structural boundary: AD-1 via "jamais écrits en base comme valeur indépendante" (schema-level absence of a field), AD-5 explicitly via "la contrainte vit dans le contrat du repository (types/API), pas seulement dans l'absence de bouton côté UI." AD-4, protecting an equally serious failure mode (accidental data loss of an in-progress session), instead relies on "aucun autre code... ne mute ni ne supprime" — a promise about code that doesn't yet exist, with no stated mechanism (a single exported delete function, a module boundary, a lint rule, a required confirmation token) that would make a stray lifecycle-triggered delete actually impossible to write rather than merely discouraged. Given the same document demonstrates the stronger pattern twice, AD-4 reads as an inconsistency in rigor rather than a deliberate choice. Fix: state the structural mechanism (e.g., "the repository's delete method is not exported outside `application/session`'s abandon handler" or "requires an explicit confirmation token parameter no lifecycle callback can supply").

### 5. [LOW] Stack table's TypeScript row is a placeholder, not a pinned decision

"TypeScript | dernière stable compatible Vite 8 (pinnée au moment du scaffold)" is the only Stack row without an actual version, unlike Vite/React/vite-plugin-pwa/Dexie which are all pinned with memlog-verified versions. This is a minor, defensible deferral (TS patch versions move fast and are usually compatibility-selected at scaffold time), but it sits in visible tension with the checklist's "no placeholder text" bar and with the rest of the same table, which otherwise holds every other dependency to a hard-pinned, verified version. Low stakes for a solo greenfield build, but worth either pinning a concrete version now (verified the same way the others were) or noting explicitly that this one row is intentionally scaffold-time-resolved and why the others aren't.

## Non-findings worth recording

The AD-3/AD-4 "resume until explicit abandon" design (persist in IndexedDB, only the Abandonner handler deletes) looks at first glance like it reintroduces PRD §6.2's explicitly out-of-scope "reprise d'une séance interrompue." It does not: EXPERIENCE.md already carries an explicit `[ASSUMPTION]` reconciling this exact tension (abandon = explicit action only; backgrounding/lock/tab-switch are never abandons), and the spine correctly turns that already-settled UX call into an enforceable architectural rule. No action needed — flagged only so this isn't mistaken for a new contradiction on a second pass.
